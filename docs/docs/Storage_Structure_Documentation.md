# AI Job Portal - Storage Structure Documentation

## 1. Overview

This document defines the storage architecture for the AI Job Portal.

The purpose is to organize raw data, processed data, AI-generated outputs,
and training datasets in a structured and scalable manner.

The storage system is designed to support:

- Resume processing
- Job description processing
- Candidate profiles
- ATS scoring
- AI screening
- Interview evaluation
- Training datasets
- Model version tracking

---

## 2. Storage Architecture

The main data storage structure is:

data/
│
├── raw/
│
├── raw_resumes/
│
├── sample/
│
├── processed/
│   ├── resume_profiles/
│   ├── jd_profiles/
│   ├── ats_scores/
│   ├── screening_reports/
│   └── interview_results/
│
└── datasets/
    ├── v1/
    ├── v2/
    └── v3/

---

## 3. Raw Resume Storage

Location:

data/raw_resumes/

Purpose:

Stores the original resumes uploaded by candidates.

Supported formats:

- PDF
- DOCX

Example:

data/raw_resumes/
├── resume_001.docx
├── resume_002.docx
├── resume_003.pdf
└── resume_004.pdf

The original resume files should not be modified.

They are treated as the source documents for the extraction process.

---

## 4. Clean Resume Storage

Location:

data/processed/

Purpose:

Stores cleaned text extracted from the original resumes.

Format:

TXT

Example:

data/processed/
├── resume_001.txt
├── resume_002.txt
├── resume_003.txt
└── resume_004.txt

The cleaned text is used as input for resume parsing.

---

## 5. Parsed Resume Profiles

Location:

data/processed/resume_profiles/

Format:

JSON

Example:

resume_001.json

A parsed resume profile contains structured information such as:

- Candidate ID
- Resume ID
- Candidate name
- Target role
- Skills
- Experience
- Education
- Parser version
- Timestamp

Example:

{
    "candidate_id": "CAND_001",
    "resume_id": "RESUME_001",
    "name": "Priya Nair",
    "target_role": "Data Scientist"
}

---

## 6. Job Description Profiles

Location:

data/processed/jd_profiles/

Format:

JSON

Purpose:

Stores structured job description information produced by the JD parser.

Information includes:

- Job role
- Required skills
- Preferred skills
- Experience requirements
- Education requirements
- Fields of study

Example:

jd_001_data_scientist.json

The structured JD profile is used by the ATS and candidate matching components.

---

## 7. ATS Score Storage

Location:

data/processed/ats_scores/

Format:

JSON

Purpose:

Stores the results generated by the ATS engine.

Example:

candidate_001_job_001.json

Information includes:

- Candidate ID
- Job ID
- ATS score
- Matched skills
- Missing skills
- Model version
- Timestamp

Example:

{
    "candidate_id": "CAND_001",
    "job_id": "JOB_001",
    "ats_score": 87,
    "model_version": "ats_v1.0"
}

---

## 10. Training Dataset Storage

Location:

data/datasets/

Purpose:

Stores versioned datasets used for AI/ML training.

Example:

data/datasets/
├── v1/
├── v2/
└── v3/

Each version represents a different snapshot of the training data.

Training datasets may use:

- CSV
- Parquet

Example:

data/datasets/v1/
└── training_data.csv

---

## 11. Metadata Standards

All important AI outputs should contain standard metadata.

### Candidate ID

Format:

CAND_###

Example:

CAND_001

### Job ID

Format:

JOB_###

Example:

JOB_001

### Model Version

Format:

module_vX.Y

Examples:

ats_v1.0
screening_ai_v1.0
interview_ai_v1.0
resume_parser_v1.0

### Timestamp

Format:

ISO 8601

Example:

2026-09-17T10:15:00

---

## 12. Candidate-Job Relationship

Candidate ID and Job ID are used together to identify a specific
candidate-job application.

Example:

CAND_001 + JOB_001

This allows the system to connect:

- Candidate profile
- ATS score
- Screening report
- Interview result

for the same application.

## 13. AI Data Lifecycle

The AI data lifecycle is:

Resume Upload
        ↓
Raw Resume Storage
        ↓
Resume Text Extraction
        ↓
Clean Resume Text
        ↓
Resume Profile Parsing
        ↓
Structured Resume Profile
        ↓
ATS Engine
        ↓
ATS Score
        ↓
Screening AI
        ↓
Screening Report
        ↓
Interview AI
        ↓
Interview Result
        ↓
Hiring Decision

The Job Description follows a parallel process:

Job Description
        ↓
JD Parser
        ↓
Structured JD Profile
        ↓
ATS / Matching System

---

## 14. Dataset Versioning

Training datasets are versioned to prevent accidental overwriting.

Example:

training_v1
training_v2
training_v3

Each version represents a snapshot of the training data at a particular point
in time.

Older versions should be retained when reproducibility is required.

---

## 15. Model Versioning

Models are also versioned.

Example:

ats_v1.0
ats_v2.0

A model version should be linked to the dataset version used for training.

Example:

training_v1
        ↓
ats_v1.0

training_v2
        ↓
ats_v2.0

This provides traceability between training data and AI models.

---

## 18. Design Principles

The storage architecture follows these principles:

1. Keep original source files unchanged.
2. Separate raw and processed data.
3. Use structured JSON for AI-generated profiles and results.
4. Use unique Candidate IDs and Job IDs.
5. Track model versions.
6. Track timestamps.
7. Maintain dataset versions.
8. Preserve traceability between candidates, jobs, models, and datasets.
9. Keep the architecture modular and scalable.
10. Support future migration to databases or cloud storage.

---

## 19. Future Production Storage

The current implementation uses a file-based storage approach for
development and prototyping.

A production system could later migrate to:

- Object storage for resumes and documents
- Relational databases for structured records
- Document databases for flexible AI outputs
- Data warehouses for analytics
- Model registries for AI model management

The current architecture is designed so that such migration can be
performed without changing the logical data flow.

---

## 20. Conclusion

The AI Job Portal storage architecture provides a structured way to store,
process, track, and version AI-related data.

The architecture connects:

Resume
→ Resume Profile
→ ATS Score
→ Screening Report
→ Interview Result
→ Hiring Decision

while maintaining Candidate ID, Job ID, Model Version, Timestamp,
